## 3. 阻塞项：异常退出后的工具进程所有权

复现步骤：

1. 在专用临时目录启动 Pi，并让真实 Agent 的 Bash 工具运行 Node 心跳夹具。
2. 等待工具事件与心跳文件，确认工具实际开始执行。
3. 对本次受控 Pi 主进程发送 SIGKILL，确认 Pi 已退出。
4. 继续观察心跳：三轮均仍在写入，说明工具子进程存活。
5. 验证工具根据夹具预先写出的 PID 显式清理 Node，再检查心跳停止。

独立证据：[真实 Agent 三轮](evidence/final/results.json)、[第 1 轮明细](evidence/final/agent-crash-active-1.json)、[直接 Bash 三轮](evidence/final/results.json)。

**已知 PID 清理只用于安全收尾，不构成通用宿主进程管理方案。** 产品不能假定工具会报告自己的 PID，也不能将 Pi 连接结束或主进程退出当作工具全部停止。

M0 收口前须增加并验证宿主的进程所有权/监督策略，覆盖正常关闭、Pi 突然退出、宿主退出和工具后代清理。只有能核实旧执行已结束，才可释放执行槽位。无法核实时保持“执行状态待核实”，禁止自动启动新任务。

本轮不引入 M1 产品协调器来绕过此门槛，也未因测试清理成功将失败案例改为通过。

## 4. 已确认的实现约束与局限

- Pi 的可执行文件存在还不够：当前安装依赖 Node。GUI 需显式定位运行依赖，不能只继承 Terminal PATH。
- Node/Pi 不自动沿用当前系统代理；首次直连请求连接超时。按已有代理配置重跑后真实任务通过。网络诊断和自动 retry 证据单独保留在 [network-diagnosis](evidence/network-diagnosis/results.json)。
- Pi 会访问配置目录并创建信任锁。独立验证配置避免了外层写入权限限制；产品正式运行需按正常用户配置权限处理。
- `abort` 与直接 RPC Bash 的 `abort_bash` 不可混用。Phase 1 的 Agent 停止路径是 `clear_queue` 后 `abort`；本轮已验证这一顺序。
- 思考级别以查询及有效配置回读为准。本机目标模型返回 low、medium、high、xhigh、max；不能因命令行接受 off 就认定该模型将其作为有效级别。
- 只读历史与执行恢复不同：历史探针不写文件；真实 Pi 的 `switch_session` 可追加 `thinking_level_change`。历史浏览不得通过执行恢复来实现。
- 分支和压缩案例使用构造 v3 文件并经真实 Pi 校验，未调用模型执行实际 compact。完整 context_edit、旧版本迁移与全部第三方扩展格式尚未覆盖；后续历史读取器必须显式声明支持范围。
- 最终统一复跑已固定源码与可执行文件 SHA-256，覆盖 30 个案例：24 个通过，6 个失败；6 个失败均为同一生命周期阻塞的两类路径各三轮复现。构建前后的源码与产物指纹已核对一致。
- 未实测原生 GUI 环境、窗口、SwiftData、VoiceOver、UI 滚动、真实 401 认证失败和限流服务端故障。精简 PATH、构造输入和网络超时不能替代这些验收。
